# The compiler, second step: Cypher from the same request, and a wider request

Status: done (2026-09-28), with the request checks; the full-set confirmation and the router are next. Follows [the compiler plan](2026-09-28-compiler.md), whose "Next"
listed both. The user asked for both, with quick tests.

## Why

The first compiler matched the free writer and was a question or two ahead where it compiled. It
compiled about 70% of questions. The rest fell back to free SQL for reasons the request couldn't
express. From the two log samples and the gold and graph-shaped questions:

- **Several fact tables** (Q01's closures and costs by site, Le6d5789b, Q08, most of the graph-shaped
  questions): the second fact can't join to the first without multiplying its rows.
- **The wrong table as the fact** (Q09, L5bac0ee7): the first measure is a distinct count on a dimension
  table (accounts), and the grouping sits on a finer table (daily delinquency). A distinct count doesn't
  change under a fan-out, so the finer table can be the fact.
- **Two steps** (Q05's month-end balance summed by product line; per-customer counts, then grouped):
  a measure computed per entity first, then aggregated.
- **A filter on a measure** (L6b9d5aa5's accounts that spent over 5,000): HAVING.
- **Two periods compared:** already expressible as two measures with a `where` on the date column, if
  the prompt says so. It needs a difference beside the ratio.
- **A Looker PDT** (`LR_{id}_site_monthly_kpis`, three questions): its canonical name isn't a valid
  alias, so the compiled SQL didn't parse. This is a bug, not a limit.

The Cypher route writes free Cypher, 3 of 10 gold. The request is route-neutral, so the same request
can compile to Cypher as well. That puts the join and definition discipline on the Cypher route, and
gives the router one request to send to either route.

## What changes

**1. The compile gets a middle step: a plan, rendered twice.** `compile.plan(request, cat, unique)`
resolves the request into blocks. Each block has:
- a fact table;
- its join steps;
- its WHERE conditions;
- its dimensions and measures (SQL expressions over table aliases);
- its per-entity step, if any.

The plan also carries the measures derived across blocks, HAVING, the order and the limit.
`render_sql(plan)` writes SQL; `render_cypher(plan, model)` writes Cypher over the Virtual Graph model.
A request that compiles to one block renders the same SQL as today, so this isn't meant to change any
answer the first compiler gave.

**2. The request, widened.** New fields, all optional:
- a measure's `per` (columns) and `then` (SUM, AVG, MIN, MAX, COUNT): computed per entity first, then
  aggregated. A latest-value Computation not asked at its own grain takes its grain as `per` and SUM as
  `then`, rather than falling back.
- `difference_of`, beside `ratio_of`.
- `having`: conditions on a measure's alias.
- a dimension's and the period's `other_columns`: the same thing in another fact's table. For
  example, the month is `fct_calls.call_date` for one fact and `month_start` for the other.
- no measures: a list of rows (the dimensions as columns, with filters, order and limit).

**3. Several facts.** The first measure's table is the fact; a measure on a table it can't join to
uniquely starts a block of its own. Each block:
- gets every dimension, from its own column, from an `other_columns` entry it can reach, or from the
  column a trusted join equates it to;
- gets the filters whose tables it can reach;
- gets the period on its own date column.

A dimension, a filter or the period a block can't reach makes the request unfit; no block silently
drops a filter. The blocks are joined on the dimensions (`FULL JOIN ... USING`, or a cross join of
single rows when there are none), and the derived measures are computed over the joined result.

**4. The fact, chosen.** When the first measure's table can't reach every table used, but another
table used can, that table is the fact. It is taken only if every measure on another table survives a
fan-out: a distinct count, a MIN or a MAX.

**5. Two steps.** An inner query groups by the dimensions and `per`, computing the measure; the outer
query groups by the dimensions and applies `then`.

**6. Aliases.** A table's alias is its name made a plain identifier (`LR_{id}_x` becomes `LR_id_x`),
and Computation expressions are rewritten to match.

**7. Cypher.** `render_cypher` takes the plan and the Virtual Graph model (`schema.json`):
- **Labels and properties:** the fact and every joined table must be labels, and their columns
  properties.
- **Joins:** each join step must be a relationship, walked forwards (from the pointing column to the
  key) or backwards on a one-to-one relationship.
- **A grouping on a join key** uses the fact's pointing column, so the relationship isn't walked and
  a fact row with no match isn't dropped. Virtual Graph has no OPTIONAL MATCH.
- **Expressions** translate from their SQL tree:
  - aggregates, IF/CASE, SAFE_DIVIDE, comparisons, IN, IS NULL and arithmetic;
  - DATE literals become `date('…')`;
  - DATE_TRUNC becomes `date.truncate`, except for Sunday weeks, which Cypher lacks.

  Anything else is unfit.
- **Other query forms:**
  - two steps become `WITH … RETURN`;
  - derived measures and HAVING sit in a `WITH` after the aggregation;
  - several blocks are unfit, since Virtual Graph has no CALL subquery.
- **The check:** the Cypher goes through the same EXPLAIN check as the free Cypher.

Unfit falls back to the free Cypher writer, as the SQL does. `navigate.writer: compiled` applies to both
routes. The request is the same LLM call either way (cached by prompt), so the Cypher compile costs no
extra LLM call.

**Not in this step:**
- two-step measures with HAVING inside (L3b82445b's "customers with three or more fees, then …");
- several facts on the Cypher route;
- a join path longer than two hops.

## How it's checked

- **Unit tests** for each new form: several facts, a dimension through another column, the chosen
  fact, two steps, HAVING, a difference, a list, the PDT alias. Each is rendered to both SQL and
  Cypher where it applies.
- **Before and after:** the first compiler's SQL for the tests' requests is unchanged by the refactor.
- **QDD, SQL:** `qdd.py writer=compiled` on both log samples and the gold questions, against the first
  compiler's results (23 and 25; gold 7) and the free writer's. Reported:
  - correct;
  - how much now compiles;
  - what still falls back.
- **QDD, Cypher:** a `--route=cypher` option on qdd.py.
  - The gold questions and the log samples, compiled against free Cypher on the same questions.
  - Only the questions whose tables are in the Virtual Graph can compile. Both writers decline the
    others alike.
  - One VG job at a time.
- **The graph-shaped questions**, both routes, compiled.
- **Run time:** minutes per run, not hours: 40 questions each, the progress printed as it goes.

## The request checks (2026-09-28)

`navigate.compile_checks` checks the request against the question before it is compiled.

**What is checked (`compile.check`):**
- **An unstated restriction.** A Computation's filter on a value the question doesn't say, such as the
  `voice` in Voice Call Transfers, for a question about all calls. The request's own filters aren't
  checked: they are the LLM's reading of the question ("cancellations" is `ACCT_CLOSE`).
- **A stated value left out.** A value the log filters a column on that the question says ("for voice
  calls"), on a column the request neither filters on nor restricts in every measure. Only these count:
  - the tables the request reads;
  - values of at least `compile_check_chars` characters;
  - no LIKE patterns;
  - no word the request's own tables and columns already name ("card" in
    `fct_card_transactions`, "purchase" in `is_purchase`).

  Grouping by the column is enough only when the question names two or more of its values.

When either check fires, the request is asked again, once, with the notes. The second request is
compiled as it comes, so a false alarm costs one LLM call, never a fallback.

**The week grain (`compile.weeks`)** is deterministic. A week follows how the log's own queries truncate
that column: BigQuery's `WEEK` from Sunday, or `WEEK(MONDAY)` / `ISOWEEK`. The question overrides it
when it names the day.

**Over the 73 quick-test questions (the cached requests, before any retry):**
- The first versions fired on 18, mostly false alarms: "card" and "deposit" matched `account_family`
  values on tables the request didn't read.
- As built, they fire on 5. Four are the wrong answers they were meant for. The fifth is right and stays
  right: its week now matches its reference's Sunday weeks.

**Results (the same questions as before):**

- **Cypher.** Two ahead of free Cypher. L6b9d5aa5 now runs: its HAVING grain is still wrong, but it no

## The router, simulated from these results

The rule:
1. **Compiled SQL when the request compiles.** Compiled Cypher is the same plan, and it can't keep an
   outer join's null group or push HAVING down.
2. **Otherwise free Cypher, when it answers** rather than declines. This covers the neighbourhood and
   path questions the request can't express.
3. **Otherwise free SQL.**

Over the stored per-question results:
- **The 40 quick-test questions:** 30 correct, the same as SQL alone. Free Cypher answers none of the
  questions that don't compile there: it declines them, or the Virtual Graph doesn't cover them.
- **The ten graph-shaped questions:** 7 correct, against 4 for SQL alone and 7 for free Cypher. The rule
  takes the better route on both sets.

So the router can be this deterministic rule. The System 1 decider in [the router plan](2026-09-26-router.md)
isn't needed for the choice between the routes.

## The full set, on Sonnet 5.5 (2026-09-28)

The query model is now Sonnet 5.5 (`claude-sonnet-5-5`), which the user asked for before the full run.
- **No forced tool.** It rejects `tool_choice` "tool" and "any". The client finds this on the first call
  and asks for the same schema as a structured output (`output_config.format`, every object closed).
- **Thinking can't be turned off.** `llm.query_thinking: between_tools`, its lowest, sends a single
  answer unthought, as Sonnet 5 ran.
- **A reply cut off at the token limit** leaves a structured output's JSON unterminated. The first full
  run stopped on one at question 56. The client now doubles the limit and asks again.

`writer=compiled`, with the checks and the router, over all three answer keys:

| | SQL | Cypher | routed |
|---|---|---|---|
| 176 log questions | **133** (76%) | 38 | 133 |
| gold (10) | 6 | 3 | 6 |
| graph-shaped (10) | 5 | 8 | 8 |

The free writer on Sonnet 5, the last full baseline: 129, 7 and 5 on SQL; 41, 3 and 7 on Cypher.

**The full run found one more rule, the open period.** The request filled "on or after April 22" with an
end of today (2026-07-01). The filled data runs to 2026-07-13: 2,082 loan decisions and 17,049
attributions fall after today. A period ending today that the question doesn't end is now open
(`compile.open_period`). The 54 questions whose queries ended on today were rerun with it, from the
cached requests:
- SQL went from 127 to 133, six regained and none lost;
- the results above include it.

**What's left, on the SQL route:**
- **Compiled:** 154 of 176 (88%), 121 correct.
  - Against the Sonnet 5 free baseline, 11 gained and 7 lost.
  - The losses: a grouping the question implies, left out (L8ee70d9a's site); an extra grouping
    (Le59b2970's `txn_type`); a unit conversion the request can't express, written as nonsense instead
    of declined (Le166be49's minutes); and the log's LEFT JOIN where a reference joins inner (La6c932d6,
    Ldfe49bfa). Joining inner everywhere cost five in the first compiler's tests, so the log's join type
    stays.
- **Gold Q05** now compiles, and wrongly: the request chose `legacy_edw.EOM_BAL_SNAP`, a frozen legacy
  table, and no month. Navigation ranks frozen tables last, but nothing tells the request a table is
  frozen. Marking frozen tables in the request's options is the next fix. It changes every request's
  prompt, so it needs a full run.
- **The model's share is unmeasured.** The free writer hasn't run on Sonnet 5.5, so the gain from the
  compiler and the gain from the model can't be separated.

**The router** sent 2 of the 176 to Cypher. Where the request doesn't compile, free Cypher almost always
declines, or the virtual graph doesn't cover the question. On the graph-shaped questions it takes
Cypher's 8.

**Cypher, compiled:**
- Of the 69 log questions it compiled, 38 are correct.
- Five hit Virtual Graph's transaction memory cap: a date truncation or HAVING that Virtual Graph
  evaluates in Neo4j, over every row.
- The rest are mostly the outer join's null group, which Virtual Graph can't keep (no OPTIONAL MATCH).
