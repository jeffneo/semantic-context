# Why `qlsc ask` gets the wrong answer, and what to change

Status: in progress (2026-09-26). Done: Sonnet 5 writes the queries (`llm.query_model`); the ruler is
fixed (Phase 1: unique names, key grouping, pivots, accepted alternative readings, no row cap); the
examples are the log's queries closest to the question, none reading a sandbox or frozen table, and
their tables join the cohort. Result: SQL 6 of 10 (was 2), Cypher 3 of 10 (was 1), either 7; the
navigated cohort now does as well as the answer key's own tables (6 and 6).

## What was measured

`eval/execution.py` scores `qlsc ask` against the reference answers. `eval/diagnose.py` runs the SQL
route twice per question: with the cohort navigation finds, and with the answer key's own tables
(perfect retrieval). Ten gold questions are scored by value.

| | correct |
|---|---|
| SQL, navigated tables | 2 |
| SQL, the answer key's tables | 1 |
| Cypher over the virtual graph | 1 |

**Perfect retrieval does not help.** Given exactly the right tables, the SQL is still wrong on 9 of 10.
Retrieval is a problem, but not the main one.

## Why each answer is wrong

Reading every query (navigated and oracle, 20 answers):

| cause | where | count |
|---|---|---|
| a filter the question did not ask for, or a guessed value | Q04 `customer_status = 'A'`, Q07 `entity_type = 'CARD'`, Q11 `platform = 'mobile'` (the data says iOS, Android) | 3 |
| a trap: sandbox copy or legacy table | Q02, Q04 (`customer_360_final`), Q05 (`EOM_BAL_SNAP`) | 3 |
| a table the answer needs was not found | Q01 (`fct_contacts_all`), Q04 (`dim_customer`), Q08 (`fct_campaign_attribution`) | 3 |
| answered a different question: copied an example query | Q01 oracle: a weekly abandon rate, from the example the log offered | 1 |
| time or grain wrong | Q01 ignores "last year"; Q09 counts delinquency over every day, not the latest snapshot | 2 |
| a SQL error the one retry did not fix | Q05 oracle: DATE vs DATETIME | 1 |
| the question is ambiguous, and the reference chose | Q02 "high-balance", Q12 "affluent" (does it include private banking?) | 2 |
| **the ruler, not the answer** | Q08, Q09: the references group by branch or campaign *name*, but 171 branches share 14 names and 5,200 campaigns share 7 (a generator shortcut); Q14 oracle: the right numbers, pivoted into columns | 3 |

Two data gaps also sit underneath:
- Q01's "last year" needs Genesys calls from late 2025, which the fill doesn't have.
- Q05's month-end logic exists in the log only in the deprecated legacy chain.

## The fundamental problems

1. **The ruler is unreliable.**
   - Non-unique names in the data, and references that group by them.
   - A matcher that can't see a pivoted answer as the same.
   - Questions with more than one fair reading.

   Before any method change, the measurement must be trustworthy, or we tune against noise.
2. **The SQL writer has no semantic contract.** It gets tables, columns and whole example queries, and
   writes free SQL. It doesn't know, and so improvises:
   - what the business's measures are (a closure call is `is_account_closure_call`; card spend is
     `SUM(amount)` over purchases; delinquency is 30+ days on the latest snapshot);
   - which tables are canonical and which are copies;
   - each table's grain;
   - which filters are standard.

   The stray filters, copied examples, wrong grain and traps all come from here.

   Yet the log knows most of this. Every gold question's measure appears in it (closure calls in 8
   query templates, confirmed fraud in 6, card spend in 5), used by production or by analysts, and the
   parse records already tag each column's role: aggregate, group, filter.

   **The semantic layer today is a navigation index: it finds tables. It is not yet a semantic model:
   measures, dimensions, entities, time.** That is the gap.
3. **Retrieval ranks tables, not answers.** The round-robin cohort represents every group, which pulls in
   copies and sandboxes and can miss the dimension a question groups by. It has no idea of canonical
   versus derived.

## The proposal

### Phase 1: a trustworthy ruler (small)

- **The generator:** unique branch names (city plus a number) and unique campaign names.
- **The references:** group by keys, with the name alongside.
- **The matcher:** compare answers as facts (dimension values → measure) after melting pivots, so shape
  doesn't matter.
- **Ambiguous questions** (Q02, Q12) get the alternatives the business itself uses (the reverse-ETL
  audience, the marketing extract's `IN ('affluent', 'private')`). An answer matching any of them counts.

Then re-baseline. Some of today's "wrong" become right, and the rest are real.

### Phase 2: a usage-derived semantic model (the change of approach)

Mine from the log, like everything else:
- **Measures:** aggregate expressions the business repeats, with the filters that come with them and the
  principals who use them (production's own definitions first).
- **Dimensions:** the columns queries group by. A dimension on a Variable joins by its key and shows its
  name.
- **Time:** each fact's date column (the partition column, and what queries filter on).
- **Canonical tables:** per entity, the table production writes and keeps current; copies and frozen
  tables are marked as such.

This is what dbt's metrics, LookML or Cube define by hand. Here it's inferred from use. It is also the
natural home for the traps: a measure defined only on a frozen table (Q05) is flagged as such.

### Phase 3: questions become semantic queries

The LLM no longer writes free SQL.
- **The choice:** it picks, from typed options, the measure, dimensions, filters (values from the
  data) and period.
- **The compile:** a deterministic compiler turns that choice into SQL for the warehouse, or Cypher for
  the virtual graph.

Both routes then carry the same meaning. The router chooses on coverage, cost and latency between two
answers that agree, which is the case where a router makes sense. Choosing measures and dimensions from
typed options is also the decision shape Jev and similar models are built for.

Free SQL stays as the fallback for questions the model can't express, and says so.

## Decisions needed

1. **Phase 1 now?** It regenerates `BRANCH` and `braze.campaign`, and recomputes what reads them (a few
   GiB).
2. **Phase 2's graph model.** `Measure` as a label (a business reader knows "Card Spend"), or
   measures as properties on columns. Dimensions and time need no new labels (properties on Column and
   Table).
3. **Scope of Phase 3:** start with aggregate questions over one fact table (7 of the 10 scored) before
   multi-fact ones (Q01's closures and costs).
