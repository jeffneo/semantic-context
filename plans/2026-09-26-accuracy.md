# Why `qlsc ask` gets the wrong answer, and what to change

Status: in progress (2026-09-27). The larger ruler is built: on 176 questions written from the log,
SQL 126 correct (72%), Cypher 36 (see "Where it stands"). Before that (2026-09-26): Done: Sonnet 5 writes the queries (`llm.query_model`); the ruler is
fixed (Phase 1: unique names, key grouping, pivots, accepted alternative readings, no row cap); the
examples are the log's queries closest to the question, none reading a sandbox or frozen table, and
their tables join the cohort. Result: SQL 6 of 10 (was 2), Cypher 3 of 10 (was 1), either 7; the
navigated cohort now does as well as the answer key's own tables (6 and 6).

## What was measured

`eval/execution.py` scores `qlsc ask` against the reference answers. `eval/diagnose.py` runs the SQL
route twice per question: with the cohort navigation finds, and with the answer key's own tables
(perfect retrieval). Ten gold questions are scored by value.

| | correct |
|---|---|
| SQL, navigated tables | 2 |
| SQL, the answer key's tables | 1 |
| Cypher over the virtual graph | 1 |

**Perfect retrieval does not help.** Given exactly the right tables, the SQL is still wrong on 9 of 10.
Retrieval is a problem, but not the main one.

## Why each answer is wrong

Reading every query (navigated and oracle, 20 answers):

| cause | where | count |
|---|---|---|
| a filter the question did not ask for, or a guessed value | Q04 `customer_status = 'A'`, Q07 `entity_type = 'CARD'`, Q11 `platform = 'mobile'` (the data says iOS, Android) | 3 |
| a trap: sandbox copy or legacy table | Q02, Q04 (`customer_360_final`), Q05 (`EOM_BAL_SNAP`) | 3 |
| a table the answer needs was not found | Q01 (`fct_contacts_all`), Q04 (`dim_customer`), Q08 (`fct_campaign_attribution`) | 3 |
| answered a different question: copied an example query | Q01 oracle: a weekly abandon rate, from the example the log offered | 1 |
| time or grain wrong | Q01 ignores "last year"; Q09 counts delinquency over every day, not the latest snapshot | 2 |
| a SQL error the one retry did not fix | Q05 oracle: DATE vs DATETIME | 1 |
| the question is ambiguous, and the reference chose | Q02 "high-balance", Q12 "affluent" (does it include private banking?) | 2 |
| **the ruler, not the answer** | Q08, Q09: the references group by branch or campaign *name*, but 171 branches share 14 names and 5,200 campaigns share 7 (a generator shortcut); Q14 oracle: the right numbers, pivoted into columns | 3 |

Two data gaps also sit underneath:
- Q01's "last year" needs Genesys calls from late 2025, which the fill doesn't have.
- Q05's month-end logic exists in the log only in the deprecated legacy chain.

## The fundamental problems

1. **The ruler is unreliable.**
   - Non-unique names in the data, and references that group by them.
   - A matcher that can't see a pivoted answer as the same.
   - Questions with more than one fair reading.

   Before any method change, the measurement must be trustworthy, or we tune against noise.
2. **The SQL writer has no semantic contract.** It gets tables, columns and whole example queries, and
   writes free SQL. It doesn't know, and so improvises:
   - what the business's measures are (a closure call is `is_account_closure_call`; card spend is
     `SUM(amount)` over purchases; delinquency is 30+ days on the latest snapshot);
   - which tables are canonical and which are copies;
   - each table's grain;
   - which filters are standard.

   The stray filters, copied examples, wrong grain and traps all come from here.

   Yet the log knows most of this. Every gold question's measure appears in it (closure calls in 8
   query templates, confirmed fraud in 6, card spend in 5), used by production or by analysts, and the
   parse records already tag each column's role: aggregate, group, filter.

   **The semantic layer today is a navigation index: it finds tables. It is not yet a semantic model:
   measures, dimensions, entities, time.** That is the gap.
3. **Retrieval ranks tables, not answers.** The round-robin cohort represents every group, which pulls in
   copies and sandboxes and can miss the dimension a question groups by. It has no idea of canonical
   versus derived.

## The proposal

### Phase 1: a trustworthy ruler (small)

- **The generator:** unique branch names (city plus a number) and unique campaign names.
- **The references:** group by keys, with the name alongside.
- **The matcher:** compare answers as facts (dimension values → measure) after melting pivots, so shape
  doesn't matter.
- **Ambiguous questions** (Q02, Q12) get the alternatives the business itself uses (the reverse-ETL
  audience, the marketing extract's `IN ('affluent', 'private')`). An answer matching any of them counts.

Then re-baseline. Some of today's "wrong" become right, and the rest are real.

### Phase 2: Computations, a usage-derived semantic model (the change of approach)

Mined from the log, like everything else. One new label, **`Computation`**: something the business
computes, repeatedly, from its columns. Its `kind` says which:

| kind | example | what it fixes |
|---|---|---|
| `measure` | card spend = `SUM(amount)` over purchases; confirmed-fraud share | a measure computed the business's way |
| `dimension` | a delinquency bucket from days past due; a month from a posting date | a grouping the business derives, not stores |
| `population` | marketable affluent customers = `segment IN ('affluent', 'private') AND email_opt_in` | a filter the business applies together, every time (Q12) |

Each Computation has:
- a name, a description and an embedding;
- its expression, as the parser normalizes it;
- the filters and grain it comes with;
- `COMPUTED_BY` links from the query shapes that compute it, so who uses it (production first) and how
  often come from the shapes.

It is linked to the columns it reads (`READS`). Two shapes computing the same expression share one
Computation. A Computation defined only on a frozen or sandbox table is flagged, like the table.

Extraction is hybrid:
- **The parser** gives each SELECT's output expressions (aggregates, CASE derivations, date truncation),
  its filters and its grouping. Its lineage tracing (`trace_expr`) is applied to writes today and works
  on any SELECT.
- **Haiku** names each distinct expression, writes its description, and judges which are the same
  computation written differently. That's about 1,100 shapes and about $1.

"Measure" was too narrow: Q09's delinquency is a derived dimension and a measure over it, and Q12's miss
is a population. Dimensions that are stored columns, and each fact's time column (its partition column,
and what queries filter it on), stay properties on Column and Table. They need no label.

**The OKF export** is part of this phase. Computations are the business concepts OKF (Google's Open
Knowledge Format) carries, as markdown files with YAML frontmatter:
- a measure becomes a `Metric` concept, and a population or a derived dimension a concept of its own
  type;
- each links to the tables it reads and to its Semantic area, following the layer's levels, with an
  `index.md` per area for progressive disclosure.

`qlsc okf` writes the bundle. It is checked by reading it back: every concept has a type, and every link
resolves.

### Phase 3: questions matched part by part

**No Question nodes, and no Dimension, Filter or Period nodes.** A question is not stored; it's
decomposed when it's asked, and each part is matched to what the layer already holds:

| part of the question | matched to |
|---|---|
| measures ("card spend") | `measure` Computations |
| groupings ("by segment") | Columns and Variables, and `dimension` Computations |
| filters ("affluent customers") | the values the log filters columns on (`FILTERS`), and `population` Computations |
| period ("last quarter") | the fact's time column |

The query writer then gets a contract, not only tables:
- the matched Computations' expressions, filters and grain;
- the join paths between them (Variables);
- the values to spell;
- the time column;
- the query shapes that compute those Computations, as examples.

Today's single embedding of the whole question becomes several anchors, one per part. That's the
pro: a two-part question (Q01's closures and costs) finds both parts. The con is an extra LLM call, and
an error in the decomposition carries through. The single embedding stays as a fallback, and the
evaluation compares the two.

**Later, a compiler:** once the parts are typed choices, a deterministic compiler can write the SQL,
or the Cypher for the virtual graph, from the contract, so both routes carry the same meaning. Free
writing from the contract stays as the fallback. That is the case where a router between two right
answers makes sense, and a typed choice is the decision shape Jev and similar models are built for.

## Where it stands (2026-09-27)

Phase 1 is done (the ruler), and so are the Sonnet 5 query writer and V2 examples (the log's closest
trusted queries). SQL 6 of 10, Cypher 3 of 10, either 7. One build, ten questions: one question moves
a score by ten points.

The SQL route's four misses:

| question | what went wrong | cause |
|---|---|---|
| Q01 | no rows | data: 2025 Genesys calls aren't filled (slice 4); navigation also missed `fct_contacts_all` |
| Q02 | no rows | copied a Looker explore query, filters and all, over a Looker table the fill left empty; missed `customer_360` |
| Q09 | the rate differs | the delinquency definition: no rule says how to count 30+ days on the latest snapshot |
| Q12 | 1,149 rows, not 1,566 | added "active, not deceased", which the business's own extract doesn't apply |

The Cypher route adds:
- the virtual graph's subset (Q05: an aggregating `WITH`);
- a non-answer (Q11: the model wrote `UNKNOWN`);
- an invented property (Q02, caught before it ran);
- a question outside the virtual graph (Q07).

Q09 and Q12 are the semantic-contract problem (fundamental problem 2): a measure's definition, and the
filters that go with it. Q01 and Q02 are data and retrieval.

The gold questions' Cypher verdicts changed overnight: still 3 of 10, but a different three (Q12 now
right; Q05, Q09 now wrong). The Cypher prompt carries today's date, so a new day missed the LLM cache
and every Cypher query was written again. Where the virtual graph lacks what a question needs, the
model now writes a stand-in (`LIMIT 1` over an unrelated label, or a literal "UNKNOWN" row) because it
has no way to decline. Two fixes to decide on:
- a way for the Cypher writer to decline;
- "today" pinned in the estate's config, so both routes are reproducible.

### The larger ruler (2026-09-27)

176 questions, each written by Sonnet from one of the log's own queries (`eval/log_questions.py`),
with that query's result as the reference answer. Navigation never offers a question's own query as an
example (`trace(exclude=...)`). Out of 299 candidate queries:
- 105 aren't business questions (row dumps, null counts, freshness and duplicate checks);
- 18 more have no usable reference: 10 empty, 3 too large, 5 cut off by a row cap the question doesn't
  ask for.

The matcher also learned one rule: a naming column may be answered by another naming the same things
one to one (a site's id by its name). A measure never is. It decided 10 of the SQL route's correct
answers.

| | questions | SQL correct | Cypher correct |
|---|---|---|---|
| all | 176 | **126 (72%)** | 36 (20%) |
| every table they read is in the virtual graph | 69 | 51 (74%) | 34 (49%) |
| the cohort held every table the reference reads | 148 | 118 (80%) | 32 |
| it missed one or more | 28 | 8 (29%) | 4 |
| an example read exactly the reference's tables | 94 | 78 (83%) | 20 |
| no example did | 82 | 48 (59%) | 16 |
| from a Looker dashboard | 55 | 39 (71%) | 22 |
| from an analyst's query | 120 | 86 (72%) | 14 |

Either route is correct on 128.

What it says:
1. **The SQL route is at 72% on questions like the business's own.** That's higher than the gold
   questions (6 of 10), and expected: these questions are written from the log, often name their codes,
   and have relatives in it.
2. **The log's examples are the largest lever.** With an example over the same tables, 83%; without,
   59%. That argues for Computations (Phase 2): they carry that knowledge to questions that have no
   close relative in the log.
3. **Retrieval still matters.** When the cohort misses a table, 29%. It misses on 28 of 176.
4. **The Cypher route isn't a second right answer yet, even where the virtual graph holds every
   table:** 49% against SQL's 74% on the same questions.
   - Of its 53 wrong answers, 40 have the wrong number of rows. A traversal drops the rows whose key is
     null, where the SQL keeps them as a null group, and it adds filters (`NOT is_reversal`).
   - 35 answers are empty, and 11 failed: an aggregating `WITH`, invented properties, "UNKNOWN".

   So the router's premise (two right options) holds for about half of the virtual graph's questions.
   Cypher needs the same contract as SQL first.
5. **The SQL route's 43 wrong answers:** in 29 a column's values differ (a definition), and in 14 the
   row count differs (a filter or the grain). Both are what Computations are meant to carry.

### The Cypher route, diagnosed (2026-09-27)

Three fixes, then the 176 log questions again:
- `navigate.today` is pinned, and both routes get its calendar.
- The Cypher writer may decline.
- A label or relationship type the virtual graph lacks is rejected before `EXPLAIN`. That was 24 of
  the 35 empty answers.

SQL 129 correct, Cypher 41, with 55 declines; either route 132.

On the 69 questions whose tables are all labels in the virtual graph (`eval/diagnose_cypher.py`):

| run | correct | lenient (null-key group left out) |
|---|---|---|
| SQL, as ask runs it | 54 | 54 |
| Cypher, as ask runs it | 39 | 50 |
| Cypher, given the right labels | 38 | 48 |
| Cypher, given the right labels and the reference SQL to translate | 49 | 59 |

- **Retrieval isn't the Cypher route's problem:** the right labels change nothing (39 to 38).
- **Virtual Graph can run most of these answers:** given the logic, the route reaches 49 (59 lenient),
  close to SQL.
- **The gap is writing Cypher from the question** (39 against 49), plus the inner-join semantics of a
  traversal (11 answers differ only by the null-key group, which the subset, with no `OPTIONAL MATCH`,
  can't return), plus a few subset limits (4 declined for want of a week truncation).
- **Only 3 questions go to Cypher alone** of the 176. The route adds no analytic reach, only a second
  translation.
- **Cypher as a second opinion is inconclusive.** `eval/agreement.py` compares the two answers with
  each other, and it is too strict to judge: when both routes are right, it calls them agreeing only
  11 times in 38.

### Graph-shaped questions (2026-09-27)

Ten questions written by hand, not from the log (`eval/graph_questions.yaml`):
- an entity's neighbourhood;
- several hops;
- shared neighbours (the merchants two customers share, the agents who share customers);
- stars around one fact.

Cypher 7 of 10, SQL 5. The SQL route took wrong join paths: a customer's accounts through raw
core-banking and Salesforce staging tables, a site filtered as `site_id = 'Tulsa'`, a customer segment
read off the queue. The virtual graph's relationships are the trusted joins, so Cypher followed them.

Ten questions is a direction, not a result. It's where the virtual graph earns its place: questions of
relationships, over a curated model.

Two gaps in the fill surfaced:
- `dim_customer.preferred_branch_id` is empty for every customer, so `PREFERS` has no edges;
- every deposit is processed at its account's own branch, and every call is handled by an agent at the
  servicing site.

Questions about those differences have empty answers, and three were replaced.

### Computations and decomposition, a quick test (2026-09-27)

`qlsc computations` found 1,255 Computations in the log's 1,194 successful shapes:
- 780 measures, 432 populations and 43 dimensions;
- 569 of them health checks (every query computing them returns one ungrouped row of aggregates);
- 686 business Computations left.

`qlsc okf` writes them as an OKF v0.2 bundle (1,517 concepts, 0 untyped, 0 broken links).

SQL route, the 10 gold questions and every sixth log question (30), `eval/qdd.py`:

| variant | gold | log sample |
|---|---|---|
| one embedding of the question (today) | 7 | 22 |
| + the 5 closest Computations as definitions, and their tables | 6 | 21 |
| + the same, without their tables | 6 | 23 |
| the question in parts (`anchors: parts`), each part navigated | 7 | 23 |
| parts + Computations matched per measure and filter | 6 | 21 |
| the same, health checks left out | 6 | 21 |

Directionally:
- **The decomposition is about even,** perhaps slightly better: it found Q08's attribution table,
  which the single embedding missed.
- **Computations as definitions don't help yet.** A close look-alike displaces what the question needs.
  - For Q08, the writer got "Approved Credit Applications", a count on the applications table.
  - No query in the log counts card applications attributed to a campaign, so no right definition
    exists to offer.
  - A definition that is near but not the thing does more harm than none.
- **What would change that:**
  - offer a definition only above a similarity threshold, and say none fits otherwise;
  - merge Computations that mean the same thing (three spellings of "Overdraft And NSF Fees");
  - keep literal values out of names ("Manila Account Closure Calls").

  Then retest.

Both stay off by default (`navigate.anchors: question`, `navigate.computations: 0`).

**The three fixes, then the same test:**
- A similarity floor (`navigate.computation_min_similarity`, 0.8), with the writer told to use a
  definition only if it computes exactly what's asked.
- Equivalent Computations merged: near neighbours by embedding, confirmed by Haiku. 8 of 21
  candidate sets merged, one wrongly (a Looker count joined to one on the stale-score table).
- Parameters kept out of definitions. A filter whose value varies between a query's runs is the
  question's, not the definition's (73 dropped). Names leave out filter values and groupings.

| variant | gold | log sample |
|---|---|---|
| one embedding of the question (today) | 7 | 22 |
| + the 5 closest Computations as definitions | **7** | **24** |
| the question in parts | 7 | 23 |
| parts + Computations matched per part | **7** | **24** |

- The definitions went from a slight loss to a slight gain.
  - They gained two log questions (average handle time, purchase cardholders) and lost none.
  - Q02 moved from wrong to empty.
  - Q08's look-alike no longer passes the floor, so Q08 stays right.
- Parts add nothing on top of the definitions here.
- Forty questions: a direction, worth confirming on the 176 before turning anything on.

## Decisions (2026-09-27)

1. **A bigger ruler first: yes.** In progress: 181 questions written from the log's own queries,
   `eval/log_questions.py` and `eval/log_accuracy.py`.
2. **`Computation` rather than `Measure`,** with the OKF export in Phase 2.
3. **Decomposition matches parts of a question to the layer;** it adds no labels (Phase 3 above).
4. **The data gaps** (Genesys history for Q01, the Looker table for Q02) are filled when the work gets
   there, not left for a later slice.
5. **The ontology:** a test first. The aligned Concepts' definitions go to the query writer in a separate
   run, compared with the same run without them; nothing changes in `ask` unless it helps.
