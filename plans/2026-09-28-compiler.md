# The compiler: questions as typed requests, compiled to SQL

Status: built and quick-tested (2026-09-28); off by default until confirmed on the full set. The accuracy plan's Phase 3. The user agreed the design and asked for
it to be built and quick-tested.

## Why

Most of the SQL route's wrong answers are the query writer's, not retrieval's. The accuracy plan's
diagnosis of the 43 misses on the 176 log questions:
- **29, a definition:** a measure computed differently, so a column's values differ.
- **14, a filter or the grain:** the row count differs.
- **Also:** wrong join paths on multi-hop questions (the graph-shaped questions), and stray filters
  (Q12's "active, not deceased").

The LLM writes free SQL, so it can do all of these. Hints (Computations as definitions, the ontology's
terms) moved the score by one to three questions, because the writer can still ignore them or
over-apply them.

The compiler takes the writing away from the LLM. The LLM fills a typed request, choosing from options
the semantic layer offers. Deterministic code turns the request into SQL:
- the joins come from the layer's trusted joins, never guessed;
- a measure the log defines comes with its definition, exactly;
- a filter is only what the request states.

## The request

The LLM (`llm.query_model`) gets:
- the question and its calendar;
- the cohort's tables and columns (with the values the log filters them on);
- the closest Computations (measures, derived dimensions, populations);
- the tables they read.

It returns one of two things. The first:

```
fits:       true
measures:   each an alias and one of:
              a Computation (by id): its expression, and its filters, exactly as the log computes it
              an aggregate: COUNT, COUNT_DISTINCT, SUM, AVG, MIN or MAX over one column, optionally
                only over rows matching conditions (COUNTIF-style)
              a ratio of two other measures (SAFE_DIVIDE)
dimensions: each an alias and a column, optionally truncated to a grain (day, week, week from Monday,
            month, quarter, year), or a dimension Computation
filters:    each a column, an operator (=, !=, IN, NOT IN, >, >=, <, <=, IS TRUE, IS FALSE, IS NULL,
            IS NOT NULL) and values, or a population Computation
period:     a date column and from and to dates, when the question names a period
order, limit: only when the question asks for a top N
```

The second is `fits: false` with a reason. That covers questions the request can't express: a list
of rows with no measure, a comparison across two periods, a subquery.

## The compile

1. **The fact:** the table of the first measure. Every other table the request names must join to it.
2. **The joins:** a path of at most two hops, over the layer's trusted joins between the tables
   available (JoinKeys with an identity-preserving, non-suspect confidence).
   - Each hop must reach a table that is unique on its join column, checked in the warehouse once and
     cached, so a join can't multiply the fact's rows.
   - Joins are inner, as analysts write them; a dimension on the fact itself keeps its null group. (First
     built as LEFT JOINs, which added a null row the references lack.)
3. **Aliases:** each table's alias is its own name, so a Computation's expression
   (`SUM(fct_card_transactions.amount)`) drops in as it is.
4. **Filters and measures:**
   - Filters every measure shares go in `WHERE`, with the request's filters and the period.
   - A measure's own filters wrap its aggregate's argument (`SUM(IF(f, x, NULL))`), so two measures
     with different definitions sit in one query.
5. **Literals** are typed from the column: text quoted, dates as `DATE '...'`, booleans and numbers as
   they are. A period on a timestamp column filters on its date.
6. **The rest:** `GROUP BY` the dimensions, then the request's order and limit. The result is parsed
   back (sqlglot) and dry-run.

**Falling back to free SQL** (today's writer), so no question is lost:
- `fits: false`;
- a name the layer doesn't have;
- a table with no join path, or a join that would multiply rows;
- a failed dry run.

The answer records which writer produced it and why.

## Where it lives

- `src/qlsc/compile.py`: the request schema, validation and the SQL compile. Pure apart from the
  uniqueness check, which goes through the connector.
- `navigate.writer: free | compiled`: which writer the SQL route uses. The default stays `free` until
  the quick tests say otherwise.
- `prompts/compile_system.md` and `compile_request.md`.

Not in the first version:
- **Cypher from the same request.** It's the next step, once the SQL compile shows its value. The
  request is route-neutral: the fact is a label, a join is a relationship, a column is a property.
- **Several fact tables** in one question (Q01's closures and costs). Those fall back.

## How it's checked

- **Unit tests** of the compile: joins, conditional measures, literals, grain, fallbacks.
- **Quick A/B** (`eval/qdd.py writer=compiled`):
  - the 10 gold questions and every sixth log question, against the free writer on the same
    questions;
  - then a second log sample (a different offset) if the first is promising;
  - the ten graph-shaped questions, whose SQL misses were join paths.
- **Reported:**
  - correct;
  - how often the request fit and compiled;
  - what fell back, and why;
  - for each answer that moved, what the request chose.

## As built, and the quick tests (2026-09-28)

**Fixes the tests forced, all in the compile rather than the request:**
- **Open-ended periods** ("since April 9"): the request has a start and no end. The first version
  dropped them silently.
- **Join type from the log.** Each trusted join takes the type most of the log's queries use for it.
  An outer join keeps the fact's rows with no match as a null group; an inner join drops them.
  - LEFT JOINs everywhere lost two answers to an extra null row.
  - Inner joins everywhere lost five to a missing one, where Looker's references LEFT JOIN.
- **Conditions inside a measure** ("count only clicked rows") stay inside its aggregate, so a group
  with none still shows zero. Moved to `WHERE`, one answer came back empty.
  `COUNT(DISTINCT x)` is wrapped inside the `DISTINCT`.
- **Other rules:**
  - a `COUNT(*)` of rows takes its fact from the dimensions or filters;
  - a value naming a column compares two columns;
  - aliases become plain identifiers;
  - a missing limit may come as `"null"`.
- **A latest-value Computation** (`ARRAY_AGG ... LIMIT 1`) compiles only at its own grain; Q05's
  month-end balance needs two steps. The prompt says such a question doesn't fit.

**Results (SQL route; free = today's writer on the same questions):**

| | free | compiled |
|---|---|---|
| gold, 10 scored | 7 | 7 |
| log sample, every sixth (30) | 22 | 23 |
| log sample, every sixth from the fourth (29) | 25 | 25 |
| the questions that compiled (56 of 59 log, over both samples) | 49 | **50** (89%) |
| graph-shaped, 10 | 5 | 4 |

- **What compiled:** 70% of the log questions (56 of 79 questions across the three answer keys).
- **What fell back:**
  - lists of rows;
  - comparisons of two periods;
  - several fact tables, which covers most graph-shaped questions;
  - two-step measures.
- **The compiler is level with the free writer, a question or two ahead where it compiles.** It is
  deterministic where the free writer isn't:
  - the joins are the log's trusted ones;
  - a Computation is used exactly as the log computes it;
  - a filter is only what the request states.

  The request is also route-neutral, which is what the Cypher compile and the router need.
- **The remaining misses where it compiled:**
  - the null-group question, where the log's majority join type and the reference disagree;
  - a grouping by a non-unique name (agent name rather than id);
  - a measure misread by the request (a closure filter applied to an abandon rate).
