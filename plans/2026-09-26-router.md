# The router: which route answers a question

Status: proposed (2026-09-26).

## Why

`qlsc ask` has two routes to an answer: SQL in the warehouse, and Cypher over the virtual graph. A third
kind of question needs neither: "where do we store SSNs?" is answered by the semantic layer itself. The
router decides, per question, which route to take.

## What the execution eval says

`eval/execution.py` runs every gold question through both routes and compares the result with its
reference answer (`results/execution.md`). Of the 10 questions scored by value:

| | correct |
|---|---|
| SQL | 2 (Q11, Q14) |
| Cypher | 1 (Q04) |
| either: the best any router can do today | 3 |

The router can move the score from 2 to at most 3. The other seven fail on both routes, for reasons
routing does not touch:
- **Navigation missed a table the answer needs** (Q01 `fct_contacts_all`, Q04's SQL `dim_customer`,
  Q08 `fct_campaign_attribution`).
- **The SQL picked a trap:** a sandbox copy (Q04) or a legacy table (Q05).
- **A filter the question did not ask for** (Q07: `entity_type = 'CARD'`).
- **Ambiguity the reference settles one way:** Q12's "affluent" includes private-banking customers, as
  the business's own extract does.

Cypher's failures are routing failures: when the virtual graph lacks the table, the model answers from a
stand-in. Q09 used `Account.status_code` for delinquency, and Q14 used `dim_account` for closures. Where
the virtual graph holds what the question needs, it was right, even where the cohort was poor (Q04: one
hop reached `dim_customer`, which navigation missed).

So the order of work is: the router, and alongside it the fixes that raise both routes (trap avoidance
from the layer's own flags, the stray filters, navigation recall).

## Is routing deterministic?

Mostly. Most signals are facts the layer already has:

| Signal | Source | Deterministic |
|---|---|---|
| Which cohort tables are virtual-graph labels, and what one hop reaches | the cohort, `Table.graph_label`, `schema.json` | yes |
| Whether Virtual Graph can run the query | `EXPLAIN`: it rejects what its Cypher subset lacks | yes, after writing it |
| Whether the SQL reads a trap: a frozen table, a sandbox, a copy | usage: `write_days`, who writes it, `DERIVED_FROM` a production table | yes |
| Cost: bytes scanned | the dry run | yes |
| **Is it a question about the data, or about the catalog?** (Q06, Q13) | the question | **no** |
| **Do the virtual graph's labels cover what the question means?** (Q04 yes; Q09, Q14 no) | the question, against the labels | **no** |

The two judgment calls are small, typed decisions over a handful of options. They're what a System 1
model is built for: a decision from a fixed set of outcomes, with a calibrated probability. The
probability is the useful part. A router that is 90% sure takes one route; one that is 55% sure can run
both and compare, which the eval shows is cheap (seconds, a few MiB).

It is not a problem that needs a System 1 model for its throughput: there is one routing decision per
question, next to seconds of query time. The case for trying one here is the decision shape, calibrated
confidence, and the experience of building with it.

## System 1 models (as of 2026-09-26)

- **Jev (TypeSafe AI, announced 2026-09-15):** hosted, early access through TypeSafe's console.
  - A request is a *state* (text or structured program state) and *questions*, each typed:
    - `noul`: the probability a statement is true;
    - `choice`: up to 255 named options;
    - `score`: 2 to 10 levels.
  - It returns probabilities and a confidence, with no text generation.
  - Claimed 70 to 500 ms per request, $0.042 per million input tokens, output free.
- **OpenJev** (open source, Apache 2.0): a Jev-compatible server (`POST /v1/systemone`, the same wire
  API, so the same client works). Backends:
  - DiffusionGemma 26B-A4B on vLLM (24 GB+ NVIDIA) or MLX (Apple Silicon);
  - smaller models: `laya-1.0` (421M), `verdict-1.4` (151M), `clm-v0.1` (8B).
- **CLM-8B (Stanford and NVIDIA, Apache 2.0):** a contrastive model. It encodes the state and each
  action, and scores them by similarity; action vectors are cached. It needs an NVIDIA GPU (vLLM).
  Reported up to 9× faster than Jev, somewhat less accurate on tool calling (95.2% vs 99.2%).

This machine is an Apple M2 Max, so OpenJev's MLX backend or its small models run locally. CLM-8B does
not. Hosted Jev needs an early-access account.

## Design

`src/qlsc/route.py`. Steps:
1. **Signals (deterministic):** the cohort's coverage by labels, the traps among its tables, and
   whether a catalog route exists.
2. **Decision:** one call to a *decider* with the question and the signals as state, and the routes as a
   typed choice (`layer`, `cypher`, `sql`). It returns a route and a probability.
3. **Act:**
   - **Confident:** take the route. A Cypher query `EXPLAIN` rejects falls back to SQL.
   - **Unsure** (below `route.both_below`): run both routes, and show both answers with where they
     differ.

Deciders, chosen by config (`route.decider`), all behind one interface:
- `rules`: the deterministic baseline.
  - Cypher when every table in the closest groups is reachable in the virtual graph and the SQL
    cohort holds a trap.
  - SQL otherwise.
  - The catalog route never.
- `system1`: any Jev-compatible endpoint (`route.system1.url`, `.model`): hosted Jev, or a local
  OpenJev.
- `llm`: Claude with a forced tool, as a reference point for accuracy and latency.

The prompts (the state text and the option criteria) are files in `prompts/`, like every other prompt.
Parameters go in `defaults.yaml`.

## How it is judged

Ten scored questions can't tell three deciders apart. The query log can make a larger set:
1. Take each successful query shape that answers something (a SELECT with an aggregate or a filter).
2. The LLM writes the question it answers, once, cached.
3. The logged query is the reference answer.
4. Both routes run each question, and which one gets the reference's result is the best route's label.

Some 200 questions come with ground truth from usage, with no one hand-labelling them. Each decider is
scored on:
- routes chosen correctly, against the best route;
- the final answer's accuracy;
- calibration (is 80% sure right 80% of the time?);
- latency and cost.

   - Hosted Jev (needs your early-access key in `.env`).
   - OpenJev locally on this Mac: a model download, several GB for DiffusionGemma, much less for
     `laya-1.0`.
   - Both, since they share an API.
2. **The log-derived question set.**
   - It costs an LLM pass over about 200 shapes (under $1 with Haiku) and runs of both routes (a few
     GiB).
   - Its reference answers are the log's own queries, run against the filled data. Shapes on tables
     slice 2 did not fill are left out.
3. **The catalog route** (Q06, Q13) in this plan, or later. It needs answers drawn from the layer
   itself: columns, their Concepts and their lineage (hashing shows as a `FLOWS` edge through `SHA256`).
