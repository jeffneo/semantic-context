# Fill slice 2: the gold questions

Status: proposed (2026-09-26). Follows [the fill plan](2026-09-26-fill-the-estate.md), whose method,
invariant and validation carry over unchanged.

## Why

Slice 1 filled the customer-context tables, so the virtual graph and `qlsc ask --run` have rows to read.
But only 5 of the 14 gold questions (Q02, Q04, Q05, Q12, Q14) have every expected table filled. The
other nine read tables that are still empty:
- **Q01, Q10:** contact-center costs and satisfaction;
- **Q03, Q11:** web and app sessions;
- **Q06, Q13:** the legacy and KYC tables;
- **Q07:** fraud;
- **Q08:** marketing;
- **Q09:** lending.

Filling them means every gold question can be answered end to end, from the question through the
semantic trace and the SQL (or Cypher) to rows. Each question can then get a reference answer, so the
navigation evaluation can score execution accuracy (the right result), not only which tables were found.

## Scope: the closure of every table a gold question names

The targets are every table in `spec/questions.yaml` under `expected`, `acceptable` **and `avoid`**,
plus everything they read (column lineage and `sources`, as in slice 1).

The `avoid` tables are the traps: the stale score, the sandbox copies, the legacy tables. They're
included so a wrong answer returns plausible wrong rows, not an empty result that gives the mistake
away (fill plan, design point 6).

| | Tables |
|---|---|
| Slice 1 (filled) | 92 |
| New in slice 2 | 79: 33 base tables to generate, 25 models and 5 copies to compute, 16 staging views |
| Slice 1 + 2 | 171 of 324 |

Without the `avoid` tables, slice 2 would be 57 tables. The traps add 22 more, mostly `legacy_edw` and
the `sbx_*` sandboxes, plus `ml_scores.churn_score_v2`.

The 33 base tables by source:
- **fraud:** `fraud_platform` (4);
- **lending:** `loan_origination` (3);
- **marketing:** `braze` (4), `salesforce.campaign`, `amplitude_mobile.EVENTS_318842`;
- **finance:** `gl_erp` (4), `credit_bureau.consumer_attributes_monthly`;
- **contact center:** `genesys_cloud.survey_response`, `contact_center_legacy.cdr_` (shards);
- **KYC:** `aml_kyc.party`;
- **legacy EDW** (10): the CC_* family, `CUST_MSTR`, `ACCT_MSTR`, `LN_PMT_HIST`, `MKTG_CMPGN_RESP`,
  `CHURN_MDL_SCR`;
- **scores and sandboxes:** `ml_scores.churn_score_v2`, `sbx_marketing.attrition_propensity_2025`.

GA4 (`analytics_312874659.events_*`) was already in slice 1's closure but was skipped because it is
sharded. It is filled here, so the two GA4 session models (`fct_web_sessions` for Q03) finally get rows.

At the slice-1 scale (1% of entities, 0.1% of events), that's about **17 million generated rows**,
against about 10 million for slice 1.

## What's new compared with slice 1

1. **Shards.** `fill.py` learns to fill sharded tables: one load job per shard, each shard's rows dated
   on its suffix. GA4 events carry the nested records the spec describes (`event_params`, `user_id` as
   the SHA-256 hex of the online-banking login).
2. **The GA4 and legacy traps arrive.** GA4 user ids are hex, so joining them to a CIF returns nothing,
   as the spec says. The legacy cost-center ids (`CC_ID`) and site codes (`SITE_CD`) share values, so
   joining one to the other silently matches.
3. **`churn_score_v2` stops at 2026-05-15**, the planted stale score. Q02's trap is the one answer that
   looks right and is six weeks old.
4. **Legacy history before the window.** The legacy EDW tables stop at their decommission dates (the
   spec's `status`), so a query on them returns old rows, not no rows.

Everything else (populations, formats, domains from the comments and templates, computing models with
their own SQL in dependency order) is slice 1's machinery. New per-table settings go in
`spec/data.yaml` under slice 2.

## Validation

As in slice 1:
- keys unique, required columns filled, identifiers resolve at their home (except the planted orphans);
- row counts within 10% of target;
- `build/data/FILL.md` rewritten over both slices.

Then, new:

1. **The gold questions have rows.** Each question's expected tables are non-empty, and a hand-written
   reference query per question returns a plausible answer. The reference queries live in the example
   (`eval/reference/Qnn.sql`), never where qlsc reads, and become the answer key for execution accuracy.
2. **The traps bite.** Each question's avoid tables return rows, and the GA4-to-CIF join returns
   nothing. The stale score's latest date is 2026-05-15.
3. **qlsc unchanged.** `qlsc extract` gives the same catalog version, and `eval/fingerprint.py` is
   unchanged after a rebuild. Filling rows changes neither the log nor the catalog.

## Cost

- **Loads:** free.
- **Model runs:** slice 1's 28 models billed about 1.8 GiB. Slice 2's 25 models and 5 copies read bigger
  event tables. Estimate: 3 to 6 GiB.
- **Quota:** under the project's 10 GiB-a-day custom quota, but not by much when combined with a day of
  `ask --run` testing. If a run gets close, the fill stops and resumes the next day (`--steps compute`
  picks up where it left off).
- **Storage:** well under $1 a month.

## Decisions needed

1. **GA4 shards: fill the 15 that exist, or create the rest (recommended: fill the 15 that exist).**
   The deploy created the first GA4 shard and the last 14 days (2026-06-16 to 06-29), enough for
   wildcard SQL to resolve. Filling only those keeps the catalog, and so the semantic layer, unchanged.
   Q03 then has two weeks of web sessions to set against the calls, which is enough for the question.
   Creating all 272 daily shards changes the catalog: a rebuild, possibly different results, and every
   quoted number checked again. That belongs in slice 4 ("every shard"). All 33 monthly `cdr_` shards
   already exist.
2. **Include the `avoid` tables (recommended: yes).** 22 more tables, so the traps behave like traps.
   Without them, a wrong answer shows up as an empty result, which makes the evaluation easier than
   real life.
3. **Reference answers: written by hand in this slice (recommended), or in a separate evaluation plan.**
   Each reference query is a short SQL query per question, written from the spec and checked against
   the data. It is what execution accuracy scores against. Doing it here means slice 2 ends with a
   score, not just rows.
