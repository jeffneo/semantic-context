# Fennmoor Bank: the spec

The answer key. It defines a fictional US regional retail bank's BigQuery estate, down to every column:
what each table means, how the tables relate, and everything that is wrong with it on purpose. The
generators (`../generate/`) produce the estate and a query log from it; qlsc reads only the log and the
catalog and tries to rediscover what is written here; the evaluations (`../eval/`) score it against these
files. qlsc itself never reads this folder.

```bash
uv run examples/fennmoor-bank/generate/build.py
```

The build expands and validates the spec, then writes everything under `../build/` (not in git: every
file is regenerated byte for byte). It exits non-zero on any inconsistency.

| Logical tables | 324 (1,169 physical once GA4 daily and Avaya monthly shards expand) |

| Source systems | Core banking (Datastream CDC), card processor, loan origination, Salesforce, Genesys, legacy Avaya, GA4, Amplitude, online banking, Braze, fraud platform, AML/KYC, credit bureau, ERP general ledger, Workday, manual reference uploads |
| dbt | 93 staging views (generated by rule), 85 hand-written intermediate/mart/ML models |
| Mess | 20 legacy EDW tables, 8 Looker PDTs, 31 team and personal sandbox tables |
| Status | 280 active, 18 frozen, 16 dead, 4 stale, 3 write-only, 3 deprecated |
| Answer keys | 15 domains / 75 subjects, 60+ concepts, 22 findings (19 planted, 3 emergent from BigQuery's cost model), 14 gold questions |

The domain is customer-centric retail banking: deposits, cards, lending,
contact center, digital, marketing, fraud, compliance and finance.

## Design rules

**The ground truth never leaks into the warehouse.** The DDL carries no
subjects, concepts, or planted-finding notes, and table descriptions only
where a real estate plausibly has them (`bq_description`, a handful of dbt
marts). Otherwise the pipeline could read the answers out of
`INFORMATION_SCHEMA`.

**Production is correct by construction.** Every dbt model's SQL is generated
from its `from` clause and column expressions, so its lineage and joins are
exact. The builder rejects any production join across id spaces.

**Mess is deliberate and declared.** A wrong join in a human-written table
must carry `trap: <finding id>`, or the build fails. So every trap is
intentional and named in `findings.yaml`.

**Source systems keep their own conventions.** For example:

- Core banking uses `UPPER_ABBREV` names and dollars.
- The card processor uses snake case and cents, with its own `account_id`.
- Loan origination is camelCase.
- Salesforce appends `__c` to custom fields.
- GA4 has nested, sharded tables with a STRING date.

That heterogeneity is what the semantic layer has to see through.

**Honest about detectability.** Each finding says whether query logs, lineage,
schema, profiling or domain knowledge is needed to find it. Some can't be
found from logs at all (F16, F18). Those test whether the pipeline says "I
can't tell" instead of guessing.

## Column DSL

```yaml
columns:
  - "CIF_NO | STRING || customer.cif | pk required"                          # raw: no expression
  - "customer_key | INT64 | FARM_FINGERPRINT(c.cif_number) | customer.key | pk"  # derived
```

The fields are `name | TYPE | expr | concept | flags`. Flags:

- `pk`, `required`
- `pii=<kind>`, `policy=restricted`
- `unit=<cents|usd|bps|pct|sec|ms>`
- `null_after=<date>`
- `contains=<concept>@<json path>`
